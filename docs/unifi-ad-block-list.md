# UniFi's built-in Ad Block list

What the free **Ad Block** setting in UniFi Network actually blocks, where its data lives on the gateway, how UniFi keeps it up to date, how it compares with the HaGeZi lists this project uses, and what this project does with it.

Everything here was observed on one gateway, by reading its files and logs, by reading the CoreDNS program's function names and strings, and by testing on the gateway. It relies on undocumented UniFi internals and may differ on other models, firmware versions, or with a CyberSecure subscription.

| | Checked on |
|---|---|
| Date | 2026-10-18 |
| Device | UniFi Cloud Gateway Ultra |
| Firmware | UniFi OS 5.1.33 (`UDRULT.ipq5322.v5.1.33.44ce47b.260909.0025`) |
| UniFi Network | 10.6.106 |
| CoreDNS | `1.11.3-10+g74ebc1e61302` |
| Subscription | none (Ad Block on, Content Filter category set to None) |

## Summary

- Without a subscription, Ad Block is **a list stored on the gateway**, not a live cloud lookup. UniFi downloads a new version about once a day.
- The downloaded list has **73,270 hostnames** in the `ADVERTISEMENT` category. Each entry blocks **that exact hostname only**, not its subdomains.
- Blocked names get the answer `0.0.0.0` (or `::` for IPv6). Blocks from the UniFi UI block list, where this project puts its other categories, get UniFi's block page address `203.0.113.250`.
- On the test gateway, **65% of UniFi's ad entries were already blocked** by the HaGeZi-based lists. In a sample of the remaining entries, **most no longer resolve**.
- Installing a new list reloads the filter in place. With large lists this **exceeds the filter's memory limit**: the system stops and restarts it, and DNS pauses. This happened 16 times in 10 days on the test gateway.
- The list format also supports entries that **cover subdomains** (`domain_zone`). This project uses that to replace UniFi's list with the Ad Block level chosen in its menu.

## How the list gets onto the gateway

The filter program (CoreDNS) updates the list itself:

1. **10 minutes after it starts** (`first_trigger_delay_in_second 600` in its config), and then **every 24 hours plus a random 0–2 hours**, it asks `https://security_cloud.ui.com/api/v2/free/download/content_filtering/2.0.0` for the current list. The answer is a signed download URL and a sha256 checksum.
2. If the checksum is the same as in `/etc/utm/info.json`, it logs `No need to update` and stops.
3. Otherwise it downloads `content_filtering_list.<date>.tar.gz` from `cdn.ips.svc.ui.com` into a new folder under `/usr/share/ubios-udapi-server/utm/tmp/`, unpacks it, removes the old files in `/etc/utm/pre_categorized_list/`, moves the new ones in and writes `info.json`.
4. Then it **reloads its lists in place** (`plugin/pluginReload: Reload plugin: hostSet`).

New lists are published about twice a day (the file names carry the time). Between 2026-10-07 and 2026-10-15 the number of exact-name entries the filter loaded grew from 85,319 to 86,719.

At start-up, the filter reads `/etc/utm/pre_categorized_list/content_filtering_list_*.csv` if those files exist and can be read. Only if they can't does it use the copy shipped with the firmware, which is about three times larger.

A typical update in the CoreDNS log:

```
plugin/updateFile: First update files
plugin/updateFile: Get download url
plugin/updateFile: Download url: https://cdn.ips.svc.ui.com/content_filtering/2.0.0/content_filtering_list.2026-10-17-22:08:58.tar.gz?Expires=…
plugin/updateFile: Extracting content_filtering.tar.gz
plugin/updateFile: Removing old content filtering files
plugin/updateFile: Installing new content filtering files
plugin/updateFile: Content filtering files updated
plugin/pluginReload: Reload plugin: hostSet
```

## File format

Each CSV file starts with a header line and uses Windows line endings (`\r\n`):

```
category,host,type
ADVERTISEMENT,sterkrendhof.net,domain
ADVERTISEMENT,metrics.vividseats.com,domain
ADVERTISEMENT,acookie.alimama.com,domain
ADVERTISEMENT,smart.mobvista.com,domain
ADVERTISEMENT,nydailynews.d1.sc.omtrdc.net,domain
ADVERTISEMENT,api.yieldlove-ad-serving.net,domain
ADVERTISEMENT,computeractive.uk.intellitxt.com,domain
ADVERTISEMENT,ad.pr.ameba.jp,domain
ADVERTISEMENT,openx.trellian.com,domain
ADVERTISEMENT,metrics.thefa.com,domain
```

- `type` is `domain` on every row except one: `ADVERTISEMENT,0.0.0.0,ip`.
- The filter also accepts the type **`domain_zone`**, which covers the name and all its subdomains. UniFi's downloaded list doesn't use it. Found in the program (it compares the type with the text `domain_zone`) and confirmed by test: a `domain_zone` row for `example.com` also blocks `www.example.com`.
- The filter doesn't check the files against the checksum in `info.json` when it loads them. Edited files are used as they are.
- The files are sorted by category. Files 02–07 are all `ADVERTISEMENT`. Files 01 and 08 also contain other categories, and files 09–10 contain only other categories.
- 61 categories appear in total. `ADVERTISEMENT` is 76% of the rows:

| Category | Rows |
|---|---|
| ADVERTISEMENT | 73,271 |
| CIPA | 1,687 |
| PORNOGRAPHY | 1,666 |
| ADULT | 1,623 |
| NUDITY | 1,623 |
| TECHNOLOGY | 1,569 |
| VIDEO_STREAMING | 1,505 |
| NEWS_AND_MEDIA | 1,374 |
| SOCIAL_NETWORKS | 1,352 |
| ECOMMERCE | 1,313 |
| 51 other categories | 8,850 |

`category_codes.csv` has the columns `code,category,is_local,response`. Only two of its 127 categories have `is_local` set to `true`:

```
0,ADVERTISEMENT,true,UNSPECIFIED
0,APPLE_PRIVATE_RELAY,true,NXDOMAIN
```

This suggests that only these two are answered from the local file and the rest need the subscription's cloud lookup. On the test gateway, the `APPLE_PRIVATE_RELAY` hosts (`mask.icloud.com`, `mask-h2.icloud.com`) resolved normally, so that row isn't active with these settings.

## How the gateway uses it

Turning on Ad Block for a network adds the network to the `dnsfilter` ipset (IPv4), `dnsfilter6` (IPv6) or `dnsfilterMac` (single devices). DNS from those networks (TCP and UDP port 53) is redirected to CoreDNS on `127.0.0.1:1053`, or `[2001:db8:1000::1]:1053` for IPv6. The relevant part of `/run/utm/coredns_config.conf`:

```
hostSet {
    route_node 0
    exclude_domain_files /run/utm/domain_list/domainlist_1.list
    include_domain_files /run/utm/domain_list/domainlist_0.list
    block_address_v4 203.0.113.250
    block_address_v6 2001:db8:1000::fa
    categories ADVERTISEMENT
    syslog
}
```

`categories ADVERTISEMENT` is the Ad Block list. The two `domain_files` are the UniFi UI allow list and block list, where this project also adds its other categories. The block and allow list entries always cover subdomains.

At start-up the filter loads everything into one lookup table: first the Ad Block list, then the allow and block lists. The log line shows the counts, where "domain zone" means entries that cover subdomains and "domain" means exact names:

```
plugin/hostSet: coredns-host-set: Loaded 1201790 domain zone, 86719 domain, 130 category
```

### Which entry wins

Tested with names under the reserved `.example` domain:

| Situation | Result |
|---|---|
| Same name on the allow list and the Ad Block list | allowed |
| Same name on the allow list and the block list | allowed |
| Same name on the block list and the Ad Block list | blocked by the block list (`203.0.113.250`) |
| Allow list has `x.example`, a list blocks `example` | `x.example` allowed, other subdomains blocked |
| Allow list has `example`, a list blocks `c.example` | **`c.example` blocked**: the more specific entry wins |

So an allow list entry covers its subdomains only as long as no list names a more specific subdomain.

### Answers and logs

| Query | Answer | Log entry in `content_filtering.log` |
|---|---|---|
| A host on the Ad Block list (`kampyle.com`) | `0.0.0.0` (`::` for AAAA) | `"type":"dnsAdBlock","category":"ADVERTISEMENT"` |
| A subdomain of an exact-name entry (`www.kampyle.com`) | real address (not blocked) | none |
| A domain on the block list (`domainlist_0.list`) | `203.0.113.250` | `"type":"contentFilteringBlock","category":"INCLUSION"` |

The cloud client logs its state to `/var/log/coredns/coredns.log` every minute. Without a subscription it never becomes ready and makes no queries:

```
plugin/statistic: {"categoryClient":{"isReady":false,"isDebug":false,"concurrentQuery":0,"waitingCacheQuery":0,"totallyQuery":0,"avgExternalAPILatencyInMS":0}, ...
```

## The memory limit and the in-place reload

The filter runs in its own control group with a memory limit:

```
# cat /sys/fs/cgroup/utm_content_filtering_service/memory.max
277872640
```

That is 265 MB. With 1.2 million block list entries, the filter uses about 175–205 MB after a normal start.

When the updater installs a new list, the in-place reload builds the new lookup table while the old one is still in memory. With large lists, that goes over the limit. The kernel stops the filter, and UniFi's supervisor starts it again:

```
kernel: coredns invoked oom-killer: …
kernel: Memory cgroup stats for /utm_content_filtering_service:
ubios-udapi-server: process: Got process exit event for process utm_content_filtering_service
ubios-udapi-server: process: Watchdog is restarting process utm_content_filtering_service
```

On the test gateway this happened 16 times between 2026-10-09 and 2026-10-18, each time 10 minutes after the filter had been restarted to load a new block list, which is when the updater runs. Each time, DNS paused for about 20 seconds. `memory.events` counts these (`oom_kill`).

The supervisor restarts the filter about 1 second after it stops. After several restarts in a row it waits longer (`Watchdog will restart process utm_content_filtering_service in 5s`).

## Compared with HaGeZi

A UniFi entry counts as covered when it, or one of its parent domains, is on the HaGeZi-based lists. That's because a HaGeZi entry also blocks subdomains, while a UniFi entry blocks only the exact name.

| Compared with | Covered | UniFi-only |
|---|---|---|
| HaGeZi Pro alone (about 200,000 domains) | 29,721 (41%) | 43,549 |
| The lists applied on the test gateway (1,201,874 domains*) | 47,691 (65%) | 25,579 |

\* Categories on: Ad Block Pro, Botnets, Counterfeit Brands, Cryptocurrency, Cryptomining, Deceptive Ads, Gambling, Hacking, Malware, Phishing, Spyware. Lists downloaded 2026-10-18.

To see whether the extra entries still exist, 200 random names from each group were looked up through the gateway's normal (unfiltered) resolver:

| Group | Resolved | Didn't resolve (NXDOMAIN or failure) |
|---|---|---|
| UniFi-only | 85 | 115 |
| Covered by HaGeZi | 176 | 24 |

"Resolved" means status NOERROR, which includes some answers with no address, so these are rough figures. They put the UniFi-only entries that still exist at roughly 10,000. Among them are ad and tracking hosts that HaGeZi doesn't list (for example `adb.wp.pl`, `fastg8.pool.iponweb.net`), old scam domains, and some ordinary-looking sites.

## What this project does with it

By default (`REPLACE_UNIFI_ADBLOCK=1` in `blocklist.conf`), the Ad Block level chosen in the menu replaces UniFi's list:

- The chosen HaGeZi list is written as `ADVERTISEMENT,<domain>,domain_zone` rows into `/data/unifi-blocklist/state/unifi-adblock/content_filtering_list_01.csv`. UniFi's rows for other categories and a marker entry (`unifi-blocklist-adblock.invalid`) are included.
- That folder is mounted read-only over `/etc/utm/pre_categorized_list`, so the filter loads it at start-up. Ads are then blocked with `0.0.0.0` and logged as Ad Block, including subdomains.
- An empty folder is mounted read-only over `/usr/share/ubios-udapi-server/utm/tmp`. The updater's next attempt stops at its first step, without downloading, installing or reloading:

  ```
  plugin/updateFile: Creating temp dir
  plugin/updateFile: Failed to create temp dir: mkdir /usr/share/ubios-udapi-server/utm/tmp/2927757896: read-only file system
  ```

  Only the list mount, without this second one, isn't enough: the updater can't replace the files then, but it still records the new checksum and reloads, and the reload still exceeds the memory limit (tested).
- UniFi's own files stay untouched underneath the mounts. A reboot, `blocklist.sh uninstall` or `REPLACE_UNIFI_ADBLOCK=0` removes the mounts, and UniFi's list and updates are back.
- With no Ad Block level chosen, the replacement has no ad entries, so neither HaGeZi's nor UniFi's ad list is active.

## Checking it on your own gateway

Run these as root over SSH on the gateway. They only read files and write to `/tmp`.

```sh
# While this project replaces the list, /etc/utm/pre_categorized_list shows the replacement.
# UniFi's own files are still visible through a second view of /etc/utm:
mkdir -p /tmp/utm && mount --bind /etc/utm /tmp/utm
L=/tmp/utm/pre_categorized_list

# Rows per category
cat $L/*.csv | tr -d '\r' | awk -F, '$1 != "category" {print $1}' | sort | uniq -c | sort -rn

# UniFi's ad hostnames
cat $L/*.csv | tr -d '\r' \
  | awk -F, '$1 == "ADVERTISEMENT" && $3 == "domain" {print tolower($2)}' | sort -u > /tmp/unifi-ads.list
wc -l < /tmp/unifi-ads.list

# How many are covered by this project's lists; the rest go to /tmp/unifi-only.list
cat /data/unifi-blocklist/state/merged.list /data/unifi-blocklist/state/ads.list 2>/dev/null > /tmp/ours.list
awk 'NR == FNR {h[$1]; next}
     {n = split($1, p, "."); s = p[n]; for (i = n - 1; i >= 1; i--) {s = p[i] "." s; if (s in h) {c++; next}}
      print > "/tmp/unifi-only.list"}
     END {print c + 0, "covered"}' /tmp/ours.list /tmp/unifi-ads.list
wc -l < /tmp/unifi-only.list

# Updater activity, list loads and out-of-memory restarts
grep -E "updateFile|Loaded" /var/log/coredns/coredns.log | tail
cat /sys/fs/cgroup/utm_content_filtering_service/memory.events

# Ask the filter about one name. Use the gateway's own address on a filtered network:
# queries from other addresses, or to port 53, skip the filter.
dig +short -b 192.168.1.1 @127.0.0.1 -p 1053 example.com A

# Clean up
umount /tmp/utm && rmdir /tmp/utm
rm -f /tmp/unifi-ads.list /tmp/unifi-only.list /tmp/ours.list
```

`blocklist.sh why DOMAIN` also says whether a domain is blocked by Ad Block, by this project's other categories, or by UniFi's own list.
